# 3den: homepage editor prototype

A working prototype of the 3den group homepage. You can switch into edit mode, drag modules onto a 12-column grid, reorder and resize them, and use the working modules: announcements, calendar, upcoming events, chat, tasks, documents, forum, vault, list, spreadsheet, canvas, survey, presentation, Gantt chart, and relationship map.

It's plain HTML, CSS and JavaScript (ES modules). There's no framework, no build step and no dependencies.

For the ideas behind it (the building blocks, design rules, how the parts fit, and open questions), see **DESIGN.md**.

## Running it

Any static file server works. From this folder:

```sh
python3 -m http.server 8000
# then open http://localhost:8000
```

Opening `index.html` directly from disk won't work, because browsers block ES module imports over `file://`.

Checks (nothing to install if ESLint and TypeScript are on your machine): `npm run lint` (ESLint, rules in `eslint.config.js`), `npm run typecheck` (TypeScript reading the JSDoc in files that start with `// @ts-check`, settings in `jsconfig.json`), or `npm run check` for both.

## How it fits together

```
   router.js ──(URL says which space/module)──► main.js ──► setCurrentSpace()
                                                              │
          ┌─────────────── store.js ───────────────┐          │
          │  state (saved)          ui (not saved) │ ◄────────┘
          │  members, spaces[]:     editMode       │
          │    each with modules[]  spaceId        │
          └──┬──────────────┬───────────────┬──────┘
   'space'   │  'mode'      │  'layout'     │  updateModuleData()
             ▼              ▼               ▼          ▲
   space-header.js       grid.js ──► module-frame.js ──┘
   app-bar.js                           │
                                        ▼
                               modules/<type>.js render()
```

1. **One store.** All data lives in `js/state/store.js`. Other files never change state directly. They call store actions such as `addModule()`, `moveModule()` or `resizeModule()`.
2. **Events.** The store emits `'layout'`, `'mode'` and `'space'` events. The grid, header and top bar subscribe and redraw themselves.
3. **Modules own their content.** Each module type draws its own body and saves its own data through `context.saveData()`. Saving module data doesn't redraw the grid, so typing in a note never loses the cursor.
4. **Storage is swappable.** Only `js/state/storage.js` knows where the state is saved (IndexedDB). Replace its functions with API calls to move to a real backend.

## Accounts, roles and permissions

**Accounts** are the members in `state.members`, with a unique `username` (used for @mentions), an email and, for accounts made on the sign-up screen, a hashed password. The demo accounts have no password, so the sign-in screen lists them: pick Leo to be the owner of 14 Juniper Lane, Maya to be an admin there, or Theo to see it as an ordinary member. Everyone only sees the spaces they're in (`getVisibleSpaces()`); a link to anyone else's group sends you back to your own page.

*Prototype only:* passwords are hashed in the browser with SHA-256 and a salt (`js/account/password.js`). A real 3den must hash on its server with Argon2 or bcrypt.

**Roles** (`js/state/permissions.js`): every group has one owner, any number of admins, and members. Each permission names the lowest role allowed to use it, and a group can change those in Settings → Roles & permissions:

| Permission | Default |
| --- | --- |
| Edit the homepage | Admins and owner |
| Change how the group looks | Admins and owner |
| Edit the group's name and description | Admins and owner |
| Add and remove members | Admins and owner |
| Post announcements | Everyone |
| Pin announcements and forum threads | Admins and owner |
| Add to vaults | Everyone |
| Remove other people's posts and files | Admins and owner |

Module types ask through `context.can('postAnnouncements')`. Admins manage roles and the permissions table; only the owner can transfer ownership or delete the group. On a personal homepage you can do everything.

**Appearance** (`js/groups/appearance.js`) is saved on each space and applied by `applyAppearance(space)`, which sets CSS custom properties (`--font-serif`, `--font-sans`, `--color-accent`, `--radius`…) on the page. Because every module already uses those variables, a group's look reaches every module without the modules knowing about it. Uploaded cover photos are shrunk to 1600px JPEGs so they fit in browser storage.

## Messages and the Chat module

Conversations live in `state.conversations` (`js/state/messages.js`). A conversation is `direct` (two people) or `group`. A group conversation can belong to a group's homepage: then it has a `spaceId`, and its members are always that group's members, so adding someone to the group adds them to the chat.

The **Chat module** stores only `{ conversationId }`. The first time it's shown it creates the conversation, which then appears in every member's Messages. The homepage card and the Messages page both draw it with `createThreadView()` (`js/messages/thread-view.js`), and both redraw on the store's `'messages'` event, so it's literally one chat in two places. A conversation counts as read only while its messages are on screen (an IntersectionObserver), so a Chat module scrolled out of view doesn't clear your unread count.

## Spaces: groups, personal homepages and blogs

Every homepage is a **space**: each group, each account's private homepage, and each account's public blog. They're the same thing in code: a name, a list of member ids and a list of modules. The editor and the module library work in all three.

| | Group | Personal homepage | Blog |
| --- | --- | --- | --- |
| `kind` | `'group'` | `'personal'` | `'blog'` |
| Members | everyone in the group | just its owner | just its owner |
| Who can see it | members; anyone, for tabs made public | only you | anyone (`canViewSpace()` in store.js) |
| Header | group initials, "Private group · 4 members" | your avatar, "Only you can see this page" | the owner's avatar, "Public blog · @leo", their bio; visitors get a Message button |
| Modules | the group/personal set | the group/personal set | the blog set: the Text and General feeds and Carousel, then Document, Photo gallery, Upcoming events |

A module type says where it can go with `spaceKinds` (default `['group', 'personal']`); the library only lists the ones that fit the space being edited (`moduleTypesFor()` in registry.js). On someone else's blog, or a group's public tab seen from outside, `context.isVisitor` is true: modules show their content and leave out editing, and `context.saveData()` refuses with "Only members can change this." (Visitors can still RSVP to public events and like posts: those save on the event or in `state.reactions`, not through the module's data.) On a group's public tab, calendars and Upcoming events show only public events (`canSeeEvent(event, me, { publicOnly: true })`). New accounts don't get a blog at sign-up: the first visit to the Blog tab asks whether they want one (`createStarterBlog()`, from js/onboarding/welcome.js). The demo people all have blogs already.

Module types adapt to who's in the space through `context.members`. For example, the to-do module hides its people controls when you're the only member, and assigns new tasks to you.

**URLs** (`js/router.js`): no hash shows your most recent group, `#space-me` shows your homepage, `#space-juniper` shows a group (`#space-juniper--<tab>` one of its tabs), `#blog-leo` shows @leo's blog, `#module-<id>` shows a module full-page, `#settings-juniper` (or `#settings-juniper--members`) shows a group's settings, `#groups` (or `#groups-explore`) shows the Groups page, `#messages` (or `#messages-<id>`, `#messages-new`) shows Messages, `#event-<id>` shows an event's page, `#feed` (or `#feed-friends`) shows the Feed, `#join-<code>` opens a group's invite link, `#account-feed` jumps to your feed settings, and `#account`, `#new-group`, `#signin` and `#signup` do what they say. Module ids are unique across spaces, so a module link finds its own space. Switching spaces leaves edit mode.

**Recent visits:** `setCurrentSpace()` records when you open each space in `state.visits`. The Groups menu and the default page use it to put your most recent group first.

**Saved data:** the save is stored in IndexedDB under one steady key (`js/state/storage.js`) and kept through updates. When the saved shape or the sample data changes, bump `DATA_VERSION` in `js/state/upgrade.js`: an older save is brought up to date on load, new sample content is added around the person's own data, and their edits and deletions stay. Changes the normalizers can't absorb get a step in `MIGRATIONS`.

## Onboarding new people

The idea: people mostly find 3den because someone sent them something, so the first visit helps with that one thing and nothing else. The plan (with the decisions behind it) is the "Onboarding plan" tab of the plan doc.

Buttons that would save call `requireAccount({ reason, action, arrival, then })`: for a guest it opens the sign-up sheet and runs `then(newMemberId)` once the account exists. Wired into `rsvpButtons()` (rsvp.js), `reactionsBar()` (like, comment), and the space header's Join, Add friend and Message, and the join page.

Notifications for people with `textNotifications` are marked `texted: true` (nothing is really sent).
- **Arrival** (`member.onboarding`, `onboarding-state.js`): `createAccount({ …, arrival })` saves the source (`event`, `group`, `blog`, `message`, `organizer`, `host`, `organized`, `direct`), the item, and the starting layout from `layoutForArrival()`. - **Starting homepages** (`STARTER_LAYOUTS` in `js/data/starter-layouts.js`): two or three modules each. The Dashboard takes `data.sections` so a layout (or Customize, on its full page) can show only some of its parts, in order. New accounts get `standard`: Dashboard and vault, 6×14 each.

- **Welcome screens** (`welcome.js`): main.js shows the welcome splash over the homepage the first time a direct sign-up lands (welcome-splash.js), and "Dive into 3den?" instead of the Feed (or My blog) while they have no blog. ## Phones

3den's phone layout is the same app, rearranged by `css/mobile.css` (loaded last, everything inside `@media (max-width: 640px)`):

- **Tab bar** (`js/editor/tab-bar.js`, the `<nav id="tab-bar">` in index.html): Home · Feed · Groups · Messages · Blog. Blog took the place of Alerts; the bell's list opens from the top bar.
- **Top bar:** the links hide (the tab bar has them), the bell stays, and a 🔍 button (`.app-bar__search-toggle`) adds `body.is-searching` to show the search row. Going to another page folds it away.
- **Sheets:** any open top-bar menu (`.app-bar__menu.is-open .groups-menu`) becomes a sheet fixed to the bottom of the screen, with a dimmed backdrop (the wrapper's `::after`; tapping it counts as "outside" and closes the menu). The frosted blur sits on `.app-bar::before`, not the bar itself, because a blurred parent would trap the fixed sheets inside it.
- **Safe areas:** `--safe-top` and `--safe-bottom` come from `env(safe-area-inset-*)` on a real iPhone (index.html has `viewport-fit=cover`). Inside phone.html the app is loaded with `?frame=iphone` (or `?frame=iphone-se`), which sets `html.in-phone-frame` and a pretend 20 px home indicator (none on an SE).
- **Swiping between modules** (`js/editor/module-swiper.js`, the `<nav id="module-strip">` in index.html): in view mode with two or more modules, the grid gets `is-swiping`, which css/mobile.css turns into a horizontal scroll-snapping row with each module one screen wide and nearly the screen's height (the module's body scrolls inside). The chips sit in a bar fixed just above the tab bar (`--module-strip-height`; the page gets extra bottom padding while it shows). The script draws the chips from the grid's frames (a MutationObserver notices redraws), lights the one in view, adds the dots, and remembers the module you were on per homepage and tab. The List/Swipe choice is kept in localStorage (`3den.phone-homepage-layout`).
- **Editing:** the module library doesn't show while you edit. **Add modules** (next to Done, phones only) opens it as a sheet from the bottom, over the tab bar, with a dimmed backdrop; tapping a module adds it at the end of the page and closes the sheet (so do ×, the backdrop, and Esc). Drag grips are hidden there, since dragging from the list is off on touch (`openLibrarySheet()` / `closeLibrarySheet()` in `js/editor/library.js`).
- **Add to Home Screen:** `manifest.json` (standalone display, icons) and the `apple-mobile-web-app-*` tags make it open full screen from its own icon. Saved data stays in that phone's browser, like everywhere else in the prototype.
- **phone.html** is a self-contained page (its own styles and script) with the iPhone frame, a status bar with the real time, a 15 Pro / SE switch, links into the app ("Try a link someone sent you") and "Reset the demo". The app's footer links to it.

## Module sizes

A module's size is set only in the editor and saved in the state, never worked out from its content:

- `span`: width, in columns of the 12-column grid (3–12).
- `rows`: height, in rows of the grid. Each row is `--grid-row-height` (24px) plus the 16px gap, so each extra row adds 40px (5–40 rows).

The grid uses fixed-height rows (`grid-auto-rows`), and each module spans its `span` × `rows`. The module frame clips to that size, and its body scrolls when the content is taller. That way, adding twenty events to the calendar never pushes the rest of the homepage around.

Module types set their starting size with `defaultSpan` and `defaultRows`. Modules saved before heights existed fall back to `defaultRows` (see `getRows()` in `js/state/store.js`).

Two layout details follow from scrolling bodies:
- Anything inside a module that should stay visible while it scrolls uses `position: sticky`, like the note's formatting toolbar.
- Pop-up menus inside modules open in the page flow (like the vault's "+ New" menu), because a floating menu would be cut off at the module's edge.

## How dragging works

Dragging uses pointer events (`js/editor/pointer-drag.js`) instead of the browser's built-in drag-and-drop API, so the same code handles mouse, pen and touch, and it behaves the same inside embedded pages.

- A press only becomes a drag after the pointer moves 6px, so clicks on handles and library items still work.
- While dragging, `grid.js` answers "where would this land?" through `setDropHandlers()`, and draws the blue drop line. Modules that share a row are split left/right. Modules that fill their row (always the case on phones) are split top/bottom.
- Releasing over the grid drops the module. Releasing anywhere else, or pressing Escape, cancels.

## Full-page views

Any module type can offer a full-page view by adding `renderFullPage(container, context)` next to `render`. Its card then gets an expand button (↗) in the header. The page's URL becomes `#module-<id>`, so Back and Forward work and the link can be shared.

Both views get the same `context`, so they read and write the same data. When you return to the homepage, the grid redraws to pick up changes made on the full page. Every module follows the same folder pattern, for example `js/modules/kanban/`:

- `*-data.js`: the data shape and the rules (filtering, sorting, date math). No DOM, so the card and the page can't disagree.
- `*-card.js` and `*-page.js`: the two views.
- A shared drawing file when both views draw the same thing: `kanban-board.js`, `gantt-chart.js`, `relationship-canvas.js`. These take getter functions and callbacks (`getData`, `onMoveCard`…) and never save anything themselves.

**Opening at an item:** a card can call `context.openFullPage(itemId)` (for example, clicking a kanban card). The full page reads it once with `context.takeFocusRequest()` and opens with that item selected.

**Dragging inside modules** (kanban cards, Gantt bars, calendar events, relationship-map nodes) uses `trackPointer()` from `js/ui/pointer-tracker.js`: a press becomes a drag after a few pixels, Escape cancels, and the click after a drop is swallowed. Each draggable thing also has a keyboard or form alternative.

## Mentions and notifications

`@username` mentions work in any text people write. `renderText()` (js/ui/text.js) shows them highlighted, and `attachMentionPicker(field, { getCandidates })` adds the "@" suggestion list to a textarea, input or rich-text editor (pass `mentions` to `createRichTextEditor`). Only people in the group are suggested, and only they are notified.

After saving something written, call:

```js
notifyMentions({ moduleId: context.moduleId, itemId: thread.id, before: oldBody, after: newBody, where: `the thread “${thread.title}”` });
```

Only people newly mentioned are notified, so editing a post doesn't notify everyone again.

Group news needs no code in the module either: `watchGroupNews()` notices new announcement posts and new events (not entries, not invite-only ones) in group modules and notifies the members, minus anyone who muted the group (`member.mutedSpaceIds`; muting silences notifications of kind `'news'` and `'thread'` only).

Assignments need no code in the module: `watchAssignments()` listens to every module data save (`onModuleDataChange` in store.js) and, using the module type's `assignments` (below), notifies anyone newly assigned to an item. People are never notified about their own actions.

## Linked items (assignments)

When something in a group is assigned to you, it also appears on your personal homepage, in the first module of the same type. These are live links, not copies: the item stays in the group's module and your homepage reads it from there each time it draws (`js/editor/linked-items.js`).

A module type takes part by adding `assignments` to its definition:

```js
assignments: {
  items: (data) => data.cards,                                  // the list of items
  isAssignedTo: (card, memberId) => card.assigneeIds.includes(memberId),
  describe: (card, data) => columnTitle(card, data),            // optional status text
  includeOutsideGroups: false,  // optional: also look in groups you're not in (events you're invited to)
  sourceTypes: ['kanban'],      // optional: module types to collect from (Calendar and Upcoming events share events)
},
```

On a personal homepage, those modules get `context.getLinkedItems()`, `context.updateLinkedItem(link, changeFn)` and `context.openLinkedItem(link)`. Views mark linked items with `sourceTag()` / `sourceLabel()` from `js/ui/source-tag.js`.

| Module | What links | How it shows on your homepage |
| --- | --- | --- |
| To-do | tasks you're assigned | mixed into your list; check off, edit and add subtasks there |
| Calendar, Upcoming events | events you're going to, said maybe to, or are invited to (also from groups you're not in) | on your calendar and in your Upcoming events; RSVP and edit there; delete only in the group |
| Kanban | cards you're assigned | listed under your board with their column |
| Gantt chart | tasks you're on | extra striped rows; edit in the group |
| Relationship map | people and organizations you keep in touch with | listed under your map with their description |

If your homepage has no module of that type, the items don't show anywhere yet: add the module (for example, a Gantt chart) and they appear.

## Adding a module type

1. Create `js/modules/my-module/my-module.js` (plus card, page and data files as it grows) and export an object that follows the contract documented at the top of `js/modules/registry.js`. The `kanban/` folder is a good starting point.
2. Import it in `registry.js` and add it to `MODULE_TYPES`.
3. Add an icon in `js/ui/icons.js` if needed.
4. Add a section to `css/modules.css`.

If it's replacing a "Soon" entry, remove that entry from `coming-soon.js`.

## Conventions

- **Naming:** functions say what they do (`renderPost`, `handleDrop`, `findDropIndex`). Files are kebab-case.
- **CSS:** light BEM (`.block__element--modifier`), with state classes like `.is-active`. Colors and sizes always come from `tokens.css` variables.
- **Building DOM:** `h(tag, props, ...children)` from `js/ui/dom.js` instead of HTML strings. The only exception is the note's sanitized HTML.
- **Comments:** every file starts with a short header saying what it's for and, where relevant, the shape of its data.
- **Writing:** always use the Oxford comma ("Home, Blog, and Groups"), in on-screen text, docs, and comments.
- **Checks:** keep `npm run check` clean. New files start with `// @ts-check`; the files without it (55) have type errors to fix first.
- **Accessibility:** use real `<button>`, `<input>`, and `<label>` elements, give icon-only buttons an `aria-label`, and keep keyboard alternatives (click-to-add, move buttons, width menu) for everything you can drag.

## The area map

The map in Account settings → Your area and on Explore comes in two layers.

- **Street map (when the page can reach it):** MapLibre GL JS draws OpenStreetMap streets, buildings, parks, and names from **OpenFreeMap** (`tiles.openfreemap.org`, the "liberty" style): free, no API key, no accounts, no cookies. The circle, distance menu, search, and Save work the same; MapLibre handles dragging, pinching, and the keys. MapLibre's code comes from a public CDN (unpkg, then jsDelivr). OpenFreeMap sees which map tiles load and from what IP address, which is why the launch plan moves to Protomaps (below). Code: `js/ui/street-map.js`. It can't be tried in the artifact viewer or the build sandbox (both block other websites); there the built-in map below is shown instead. `tests/test_street_map.py` checks the wiring with a stand-in for MapLibre, and the fallback.
- **Built-in map (always there underneath):** drawn by 3den itself, with no map service: nothing about where you look or what you type leaves the page.

- **Land** comes from `js/data/world-land.js`: hand-simplified outlines, right at the scale of countries and rough at the scale of a city. When the page is allowed to load it, the map then swaps in finer country outlines (Natural Earth data inside the open-source `datamaps` package, from a public CDN; `loadDetail` in `js/ui/area-map.js`). That step couldn't be tried in the build sandbox, which has no network; if it fails, the built-in outlines stay.
- **Places** come from `js/data/world-cities.js`: the time-zone database's cities (every country has at least one) plus large cities added by hand.
- **For the backend (decided):** move the street map to **Protomaps** on 3den's own storage (one PMTiles file; MapLibre stays), ship MapLibre with the app instead of loading it from a CDN, and add address search with **Photon** on 3den's own server. Then no outside service sees where anyone looks. Bundle Natural Earth's outlines into the app at the same time and drop that CDN step too.

## Known limitations

- On touch screens, dragging *from the module library* is off so the list can still be scrolled with a finger. Tap a library item to add it instead. Modules already on the page can be dragged by touch.
- Uploaded files are kept in browser storage, which holds only a few megabytes. Files over 1 MB are listed by name and size without a preview. Downloading files back out isn't available in the hosted sandbox.
- PDF previews (with remembered page and highlights) aren't built yet.
- The rich-text editor (`js/ui/rich-text-editor.js`) uses `document.execCommand`, which is deprecated. The planned co-editing editor will replace it with a proper editor library and a sync layer, such as a CRDT.
- Data is per-browser. Two people on the same link don't see each other's changes yet.
- Encryption keys for every demo account live in this one browser (they'd each be on their own phone). The messages' encryption is real, but without a server there's no prekey exchange, ratchet, or multi-device.
- In the artifact viewer, a few browser features are switched off by its sandbox: file downloads (CSV, .ics, and PNG buttons), "Use my location", and device notifications. They work when the folder is served as an ordinary website.
- Instagram is simulated; a real build needs a Meta app with Instagram Login, app review, and a server that stores tokens and polls for new posts.
- On touch screens, pressing a kanban card, Gantt bar or relationship-map node starts a drag rather than scrolling the page. Scroll from the empty space around them.
- On the Gantt chart, a month's name can be partly hidden behind the task names column while that month is scrolling off the left edge.
